# ADR-0008: Metadata Extraction (meta.json) and details.json Generation

## Status
Accepted

## Date
2026-07-26

## Context
Comic book archives (`.cbr`, `.cbz`, `.zip`, `.rar`) and uncompressed book directories in the source repository may contain metadata files (`meta.json`) generated by scraping tools or cataloging software (such as hitomi/nhentai metadata formats).

Downstream reader applications and indexing services require a standardized metadata schema (`details.json`) placed alongside the generated `cover.jpg` in the output book directory (`output/local/[BookName]/details.json`).

We needed to:
1. Support reading `meta.json` both embedded inside archives and provided externally alongside archive files in `--source` (`[stem].meta.json` or `meta.json`).
2. Implement schema transformation engines (with default `--meta n20`) to normalize raw metadata into a standardized `details.json` format.
3. Handle title fallback logic, tag-based extraction for author, artist, and genre lists.
4. Maintain safe execution with file size limits (`MAX_FILE_SIZE`) and path safety (`_safe_join`).
5. Ensure books without `meta.json` continue parsing normally without error or outputting empty `details.json`.

## Decision
1. **`meta.json` Resolution Hierarchy**:
   - Check inside the archive for `meta.json` (case-insensitive search, excluding hidden/`__MACOSX` files).
   - If not found in the archive, check `--source` for `[book_stem].meta.json` or `meta.json`.
2. **Schema Engine Transformation (`n20`)**:
   - `title`: Extracted from `title.english` if present; falls back to non-English dictionary values (e.g. `japanese`), plain string `title`, or empty string.
   - `author`: Extracted from tag objects with `type` `"group"` or `"author"` (comma-separated), falling back to top-level `author` field.
   - `artist`: Extracted from tag objects with `type` `"artist"` (comma-separated), falling back to top-level `artist` field.
   - `description`: Set to `"none"`.
   - `genre`: Array of tag names where `type` is `"tag"` (or raw string tags).
   - `status`: Constant `"2"`.
   - `_status values`: Static array defining status codes 0 through 6.
3. **CLI Option Integration**:
   - Added `--meta` argument defaulting to `"n20"`.
4. **Graceful Fallback**:
   - If `meta.json` is missing or unparseable, parsing completes normally without creating `details.json`.

## Alternatives Considered

### Alternative A: Raw Copy of `meta.json`
- *Pros*: Simple copy operation.
- *Cons*: Does not normalize metadata fields across different scraper schemas for reader applications.
- *Status*: **Rejected** in favor of standardized engine transformation (`transform_meta_to_details`).

### Alternative B: Mandatory `meta.json`
- *Pros*: Ensures every book has a `details.json`.
- *Cons*: Fails or generates dummy files for archives without metadata.
- *Status*: **Rejected** in favor of optional metadata generation.

## Consequences
- Processed books with `meta.json` automatically include a structured `details.json` alongside `cover.jpg`.
- Books without `meta.json` remain fully supported.
- Future metadata schema engines can easily be added by extending `transform_meta_to_details` and specifying different `--meta` engine flags.
